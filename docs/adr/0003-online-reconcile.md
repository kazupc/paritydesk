# ADR 0003: Runtime spikes and the write path for each row

- Status: accepted (Week 0, first round; second round 2026-11-23)
- Date: 2026-11-22
- App versions: 6.6395.1 (first attempt), 6.28899.2 (first round), 6.28899.6 (second round)

## Context

The design (D12, D26) says no capability claim goes into the README until a spike on the real app backs it. This ADR records the first round of spikes. They were run on one Mac with one real account, by a detached launchd job that quit the app with an Apple Event, wrote test values while the app was stopped, relaunched it and took read-only copies of Local Storage and `claude_desktop_config.json` at fixed times. Every write was preceded by a verified backup, and a final phase put the test values back.

## Results

| Spike | Question | Result | Evidence |
|---|---|---|---|

Pin order (`dframe-local-slice`, `dframe-store.pinnedOrder`) and group order (`code-projects-order.<acct>`), written to Local Storage **and** the config mirror, stayed for the whole 10-minute window. ## Findings that were not spikes

1. **Quit is vetoed while Claude is working.** If any session is mid-turn, the app answers the quit Apple Event with a dialog: "Claude is still working" — *Quit anyway*, *Wait for Claude* (default), *Cancel* — and logs `beforeQuit: vetoed by before-quit interceptor`. A message queued in the invoking session starts a new turn as soon as the current one ends, so "the turn ended" is not enough.
2. **SIGTERM is not a clean quit.** The next launch logged `Previous run did not exit cleanly`. The legacy script's SIGTERM fallback is removed; paritydesk never sends signals to the app.
3. **Chrome's native messaging host lives in the app bundle but belongs to Chrome.** `Contents/Helpers/chrome-native-host` processes are children of Chrome and outlive the app. Any "is the app still running" check that matches the bundle path must exclude them, along with `ShipIt` and `chrome_crashpad_handler`.
4. **A staged update installs on quit.** ShipIt waits for the app to exit and then swaps the bundle. A switch that quits the app while an update is staged relaunches a different version. Preflight must detect this and either refuse or wait for ShipIt to finish.
5. **Claude in Chrome is bound to one account at a time.** The app connects to `wss://bridge.claudeusercontent.com/chrome/<account uuid>`, and the extension connects to the bridge of the account it is signed in to. After a switch, the extension connects only if it is signed in to the account now in the app. Folder swapping does not affect this, and paritydesk cannot fix it without touching credentials.

## Decisions

- **Rows 9 to 11 (sidebar):** every key that the config mirrors under `preferences.epitaxyPrefs` is written to Local Storage and the config mirror together, then verified after launch. Section settings stay ON (`set_view`, `create_section`) by default; OFF writes to both copies are allowed with verification. `collapsedGroups` was not tested and stays not carried.
- **Quit (D14):** Apple Event only. Before quitting, wait until no session is working (no running turn, no queued message), then quit. If the app vetoes, wait for the user's answer up to a limit, never force. An app that answers the quit event with a cancel (AppleScript error -128, userCanceledErr, which AppKit replies when the app returns terminateCancel) or does not answer it in time (-1712; the app may hold its reply while it asks, and an unanswered Automation prompt looks the same) is waited on the same way and then watched for a late quit, since it may still quit by itself; only the `quit_vetoed` main.log line marks the dialog (and so the "your answer decides" message). It exits 10. Only -1743 and -1744 mean missing Automation (exit 15); -10004 (a sandboxed sender) or any other error exits 10 at once. The error number is kept and shown. Whether the real app's dialog makes the quit event return 0 or -128 is not yet recorded (release checklist, Busy sessions step).
- **Quiescence (D15):** the app's process set excludes Chrome's native host, ShipIt and crashpad. Writes still require no open file under `Local Storage/` or on the config file.
- **Preflight:** refuse to switch while a ShipIt update is staged, unless `--allow-update` is given, in which case wait for the install and re-run the shape probes on the new version.
- **Relaunch (P11):** reopen the invoking session with `claude://claude.ai/epitaxy/<id>`, rebuilt from a validated id (`^local_[0-9a-f-]{36}$`), and confirm it with `setFocusedSession` in main.log.
- **Identity marker (S17):** the xattr marker is used.
- **Claude in Chrome (G1):** paritydesk cannot keep one extension signed in to two accounts. The supported setup is **one Chrome profile per Claude account**, each with Claude in Chrome signed in to that account and kept open (S18 passed). The README and `init` explain it. `doctor` reports whether an extension connected to the active account's bridge after the last launch (`Chrome extension connected to bridge` in main.log) and explains the setup when it did not.

## Second round (2026-11-23, app 6.28899.6)

S7 was run on the real volume and S16 by a type check of the stored value. S5 and S6 were run in a Code session of the app: S5 with a temporary hook in the Claude Code settings, removed afterwards; S6 with the app's own sidebar tool on that session. The rest were answered by reading the app's code. S14 also used a copy of the data. Each answer drawn from the code was checked by two independent reviewers who tried to refute it. None did, though they corrected details, and those corrections are included below. The app had updated itself from 6.28899.2 to 6.28899.6 between the rounds. A comparison with the 6.6395.1 code found the same logic for S2 and S15. The manifest's 29 shape probes passed on a copy of the 6.28899.6 data for every account and org scope in it (a deliberately broken copy failed 5 of them), so 6.28899.6 is now listed as tested.

| Spike | Question | Result | Effect on paritydesk |
|---|---|---|---|
| S2 | Does a `ccd-sync-pending:<store>` marker make the app push its local value instead of pulling the server's? | **Yes.** At the first reconcile after launch, a store whose marker is `1` or `<account>/<org>` (optionally ending in `\|migrate`) sends its whole local value to the server with no `If-Match`. There is no timestamp or version rule. The only conflict handling is a merge, field by field, against `ccd-sync-pending-base:<store>`, which applies only when its stamp equals the marker. Without a marker, an existing server value is pulled over the local one. The marker is dropped when the store has no readable local value, or when the owner, org or quarantine checks fail. Some synced stores (the starred lists) live in IndexedDB, not Local Storage. | v0.1 keeps writing after launch and verifying (no change). Using the marker offline would overwrite newer server values from other devices, so it waits for v0.2. If it is used then, it needs a marker scoped to account and org, plus a matching pending-base. |
| S5 | Do Claude Code hooks fire for the tools the app injects into a Code session? | **Yes.** A temporary `PreToolUse` and `PostToolUse` hook matching every tool logged both events for the app's tools (`mcp__ccd_session_mgmt__get_session`, `mcp__ccd_turn__update_plan`), for `Artifact`, and for the built-in tools. A `PreToolUse` hook that answered `permissionDecision: deny` for `mcp__ccd_sidebar__list_groups` stopped the call before it ran, and its reason was shown in the tool error. The hook was added to the settings while the session ran and took effect at once, without a restart. | The v0.2 items that waited for S5 can be built: the PreToolUse guard, the PostToolUse capture, the in-app write path and artifact sync. Nothing changes in v0.1. |
| S6 | Does `set_pinned` need one approval card per call? | **For another session, yes, in default mode.** Pinning the invoking session itself was not prompted. There is no tool that pins several sessions at once; `move_sessions` takes up to 25 sessions in one call, but only to move them. | Pins through the tools stay a v0.2 item: diff only, one reconcile per switch, with "skip pins this time". |
| S7 | Does `RENAME_SWAP` work on the user's volume? | **Yes.** APFS with FileVault on: `VOL_CAP_INT_RENAME_SWAP` is valid and set. Swapping two folders next to the data folder exchanged them atomically, both through `~/Library` and through the firmlinked `/System/Volumes/Data` path. | The swap is the normal path. The journaled two-rename fallback stays for other volumes. |
| S13 | Can the worktree sweep of the active account delete a worktree that the other account created? | **Yes, unless the name is known.** Every 30 minutes the sweep scans the parent folders the active data folder knows. It can remove a clean, unlocked worktree that has no `.worktree-keep` file, carries the app's marker, has been untouched for 24 h, and was first seen at least 24 h earlier; it runs `git worktree remove --force`. Ignored files (`node_modules`, `.env`) go with it; commits and branches stay. It consults only the active folder's `git-worktrees.json` and the active account's sessions. A folder whose name matches a registered worktree or a session's worktree is skipped. | The worktrees row merges both folders' registries, and the sessions row carries the records, so the other account's worktrees are known by name after a switch. | S14 | Can the pinned Code sessions be read offline? | **Yes, from a copy.** The list is the `dframe-starred-code` store in IndexedDB (database `keyval-store`, object store `keyval`, key `store:pin-state:dframe-starred-code`), not in Local Storage. It can be read by parsing the raw `.log` and `.ldb` files without opening the database (comparator `idb_cmp1`). The value is a V8-serialized JSON string `{state:{starredIds}}`. Local ids are never uploaded, and account changes keep them. The app also mirrors the list into each session record as `isStarred`, but it sends only additions on launch, so stale `true` values remain. | v0.1 carries pin order, not which sessions are pinned. `isStarred` is now run state, kept from the target folder. Offline capture of pins is possible for v0.2; writes stay online. |

They are stamped at quit on sessions whose turn was open and are dropped after 24 h. On the next launch or open, the app sends a fixed "please continue" message by itself, with no prompt. For a local session it never checks whether the turn had really ended. | New role `resume_mark` (`interruptedByQuitAt`, `interruptedUnseenResume`, `interruptedByQuitFor`, `cycleClosedAtQuit`, `armedWorkAtQuit`, `cutTurn`, `cutTurnChain`): never carried to another account, and the target's own marks are dropped once the other account moved the session on (its record is newer), so a finished turn is not resumed. Continue-after-switch stays a v0.2 opt-in. |

Only its type and length were checked; the value was not decoded. | Presence check of the top-level key only (no change). |

### S1, second round: collapsed groups, and which copy wins at launch

Answered from the 6.28899.6 code, each answer checked by two reviewers who tried to refute it (one corrected a table row; the conclusions held). Not yet confirmed with a runtime test in which the server holds a value different from both local copies.

The app keeps the sidebar in three places: Local Storage (`dframe-store` and `LSS-persisted.*`), the config mirror (`preferences.epitaxyPrefs` in `claude_desktop_config.json`, which the renderer reads over IPC and prefers over `LSS-persisted.*`), and, for some fields, the account's server settings row. At launch the renderer hydrates `dframe-store` from Local Storage, seeds only scopes not yet marked `prefsSeeded` from the mirror, then runs the first reconcile with the server, then writes the result back to the mirror.

| Value | Synced to the server | Who wins at launch | An offline write by paritydesk |
|---|---|---|---|
| Section sort, group-by, ascending and order (`dframe-code-sections`, `codeSidebarByScope`) | Yes, for the active account and org | The server, when its row has the sections | Replaced at the first reconcile; other orgs' scopes stay until that org is active |
| `groupByByMode`, `sortByByMode` | Yes | The server, per mode | Replaced |
| Section collapse (`sections[].collapsed`) | No (reset before upload, kept from local on pull) | Local Storage, when the scope is `prefsSeeded` | Survives |
| Group collapse (`dframe-store.collapsedGroups`, also `openedGroups`, `collapsedFamilies`) | No | Local Storage; not in the mirror | Survives |
| Pin order of local items (`code:local_*` and other device-local ids in `pinnedOrder`, mirrored as `dframe-local-slice`) | No | `dframe-store`; the mirror only fills an empty local slice | Survives when both copies are written alike |
| Pin order of other items | Yes | The server | Replaced |
| Group order (`code-projects-order.<acct>`) | No | The mirror | Survives when the mirror is written |
| Custom groups and their order | Yes (local-session assignments stay local) | The server | Replaced, except local-session assignments |

An offline write to a synced field survives only when the account's row has no entry for the store, or its persisted version differs, or a sync-pending marker is set (S2; paritydesk never sets one).

**Effect on paritydesk:** no code change. Each account's sort, group-by and section order come from its own server row, so they cannot be made equal offline: the sidebar-view row writes them, `verify` sees them replaced and records the value as contested, and later switches do not fight it. Local pin order, group order and section collapse do carry. Group collapse is device-local and carryable offline (Local Storage only); carrying it stays a v0.2 item.
